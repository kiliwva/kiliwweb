Developer API

Programmatic access to your Kiliw Cloud storage over a simple REST API: upload, download, list and delete files and folders from scripts, CI pipelines, backups or your own apps. API access is included in the DEV plan ($12.99 / 30 days · 500 GB · files up to 50 GB).

Authentication

Create API keys in the cloud app: Profile → API → Create key (up to 5 keys per account). The secret looks like kw_… and is shown only once — store it safely. Only a hash of the key is kept on the server; a lost key cannot be recovered, only revoked and re-created.

Every request must carry the key in the Authorization header:

Authorization: Bearer kw_<your key>

Base URL: https://cloud.kiliw.com. All responses are JSON unless you are downloading a file. Without a valid key the API returns 401 unauthorized; with a key on a plan without API access — 403 plan-required.

Quick start

# who am I / how much space is left
curl https://cloud.kiliw.com/api/v1/usage \
  -H "Authorization: Bearer kw_..."

# upload a file into the folder "backups"
curl -X PUT https://cloud.kiliw.com/api/v1/files/backups/db.sql.gz \
  -H "Authorization: Bearer kw_..." \
  --data-binary @db.sql.gz

# list that folder
curl "https://cloud.kiliw.com/api/v1/files?path=backups" \
  -H "Authorization: Bearer kw_..."

# download it back
curl -o db.sql.gz https://cloud.kiliw.com/api/v1/files/backups/db.sql.gz \
  -H "Authorization: Bearer kw_..."

Endpoints

GET/api/v1/usage

The account's plan and current storage usage.

{
  "success": true,
  "email": "you@example.com",
  "plan": { "type": "dev", "maxFile": 53687091200, "quota": 536870912000, "until": 1786291200000 },
  "usage": 1073741824
}
GET/api/v1/files?path=<folder>

List one folder level. path is optional (empty = root), e.g. ?path=backups/2026. 

{
  "success": true,
  "path": "backups",
  "folders": ["2026"],
  "files": [ { "name": "db.sql.gz", "size": 10485760, "uploaded": "2026-07-10T12:00:00.000Z" } ]
}
PUT/api/v1/files/<path>

Upload a file; the request body is the file contents. Parent folders are implicit — uploading to a/b/c.txt creates the path. Set Content-Type if you want it preserved for downloads. Single-request uploads are limited to 100 MB; the plan's per-file and total-storage limits also apply. 

curl -X PUT https://cloud.kiliw.com/api/v1/files/photos/cat.jpg \
  -H "Authorization: Bearer kw_..." \
  -H "Content-Type: image/jpeg" \
  --data-binary @cat.jpg

→ { "success": true, "path": "photos/cat.jpg", "size": 482113 }
GET/api/v1/files/<path>

Download a file. The response body is the file; 404 not-found if it doesn't exist.

DELETE/api/v1/files/<path>

Delete a file. Any public share link pointing at it is removed too.

POST/api/v1/folders

Create a (possibly nested) folder.

curl -X POST https://cloud.kiliw.com/api/v1/folders \
  -H "Authorization: Bearer kw_..." \
  -H "Content-Type: application/json" \
  -d '{"path": "backups/2026"}'
DELETE/api/v1/folders?path=<folder>

Delete a folder recursively, with every file inside. Share links and edit grants for the folder are cleaned up.

Direct links (hotlink)

A direct link serves the raw file bytes at a stable URL — embed images on your site, ship download URLs in your app, or pull assets from scripts. Range requests are supported (video seeking works) and responses are cached for 5 minutes.

POST/api/v1/links
curl -X POST https://cloud.kiliw.com/api/v1/links \
  -H "Authorization: Bearer kw_..." \
  -H "Content-Type: application/json" \
  -d '{"path": "photos/cat.jpg"}'

→ {
  "success": true,
  "direct": "https://cloud.kiliw.com/f/<token>",
  "page":   "https://cloud.kiliw.com/share/<token>"
}

One link per file (creating a new one replaces the previous share settings). GET /api/v1/links?path=… returns the current link, DELETE /api/v1/links?path=… revokes it. The same direct URL also appears in the web app’s share dialog for public, non-password links. HTML/SVG are served as downloads, never rendered.

Presigned uploads

Let a browser (or any client) upload directly to your storage without your API key: create a single-use upload URL server-side, hand it to the client, the client PUTs the file.

POST/api/v1/uploads
# 1. your server creates the ticket
curl -X POST https://cloud.kiliw.com/api/v1/uploads \
  -H "Authorization: Bearer kw_..." \
  -H "Content-Type: application/json" \
  -d '{"path": "inbox/photo.jpg", "maxBytes": 10485760, "ttl": 3600}'

→ { "success": true, "url": "https://cloud.kiliw.com/up/<token>", "expires": 1786300000000 }

# 2. the client uploads straight to it (no auth header needed)
curl -X PUT "https://cloud.kiliw.com/up/<token>" \
  -H "Content-Type: image/jpeg" --data-binary @photo.jpg

Tickets are single-use and expire after ttl seconds (default 1 h, max 24 h). maxBytes caps the upload; your plan’s per-file and storage limits always apply. CORS is open on the upload URL, so browsers can PUT to it from any site.

Webhooks

Get an HTTPS POST whenever files change in your account — uploads (web, API, presigned) and deletions. One webhook per account.

POST/api/v1/webhook
curl -X POST https://cloud.kiliw.com/api/v1/webhook \
  -H "Authorization: Bearer kw_..." \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/hooks/kiliw", "events": ["upload", "delete"]}'

→ { "success": true, "url": "…", "events": ["upload","delete"], "secret": "whsec_…" }

Deliveries are JSON bodies with two headers: X-Kiliw-Event and an HMAC-SHA256 signature.

POST your-url
X-Kiliw-Event: upload
X-Kiliw-Signature: hex(hmac_sha256(secret, raw_body))

{ "event": "upload", "path": "backups/db.sql.gz", "size": 10485760, "ts": 1786300000000 }
{ "event": "delete", "paths": ["old/report.pdf"], "ts": 1786300000000 }

Verify by computing the HMAC of the raw body with your secret and comparing to the header. Deliveries time out after 5 s and are not retried — treat them as notifications, not a source of truth. GET /api/v1/webhook shows the config, DELETE removes it.

Errors

Failed requests return {"success": false, "error": "<code>"} with a matching HTTP status:

StatusCodeMeaning
401unauthorizedMissing, malformed or revoked API key
403plan-requiredThe key's account has no active DEV plan
400bad-path / bad-requestInvalid path or body (names ≤ 180 chars, depth ≤ 12, no / in names)
404not-foundNo such file or endpoint
413too-largeBody exceeds 100 MB or the plan's per-file limit
413quotaThe upload would exceed the plan's storage quota
405method-not-allowedUnsupported HTTP method for this endpoint

Good to know

  • Files uploaded via the API appear in the web app instantly, and vice versa — it is the same storage.
  • Uploaded images go through the same automatic 18+ content check as web uploads.
  • URL-encode special characters in paths (spaces → %20).
  • Revoking a key in the profile invalidates it immediately.
  • Need files over 100 MB via API, more keys or higher limits? Reach out — the plan can grow.
